**BEV Model Performance Investigation**

Split the BEV model into 6 logical blocks (CameraDeformedCylinder Backbone, CameraDeformedCylinder BEV Transform, CameraCylinder Backbone, CameraCylinder BEV Transform, BEV Aggregator, Output Heads) and tested each independently with forge optimization passes and program cache enabled. At opt_level_1 all blocks compiled and ran cleanly. At opt_level_2 the two BEV Transform blocks hung during compilation. Since both share the same architecture, the smaller one (CameraCylinder BEV Transform) was taken for deeper analysis — it produced ~2,931 TTIR ops despite the ONNX model having only ~20 ops. Profiling each op individually identified `grid_sample` as the bottleneck, with a single instance decomposing into ~362 TTIR primitives. With ~40 `grid_sample` ops in the full BEV model this accounts for ~14,480 of the 15,769 total TTIR ops. The root cause was that `grid_sample` had no native TTIR/TTNN dialect support, so TVM pattern callbacks broke it down into primitives.

Since `ttnn::grid_sample` already exists in tt-metal, native `grid_sample` support was added end-to-end in tt-mlir. On the dialect side, `TTIR_GridSampleOp` and `TTNN_GridSampleOp` were defined with their verifiers, and an OpModel stub was added. The TTIR → TTNN conversion was implemented with two important layout transformations: the input tensor is permuted from NCHW to NHWC (tt-metal `grid_sample` expects NHWC), and the grid tensor is permuted from TVM relay format (N, 2, H_out, W_out) to the tt-metal expected format (N, H_out, W_out, 2). On the serialization side, the `GridSampleOp` table was added to the flatbuffer pool schema with the op registered in the program union, and `createOp` / `emitTTNNOperation` dispatch was wired up in the flatbuffer serializer. The runtime was extended with a new `grid_sample.cpp` op handler and dispatch cases in `program_executor.cpp` and `runtime.cpp`. EmitC and EmitPy conversions were also added so the op can be lowered to both C++ and Python backends. All grid_sample configurations (bilinear, nearest, bicubic interpolation; zeros, border, reflection padding; align_corners true/false) at opt_level_0/1/2 now pass.

With GridSample resolved, testing continued at opt_level_2 for each block. Block C (CameraCylinder Backbone) was failing during compilation with a ConvTranspose2d fatal: `get_cb_info expects conv_config.weights_dtype to be already set`. Block C has four ConvTranspose2d ops (in_ch=192, out_ch=192, kernel=2×2, stride=2×2) covering input sizes from 1×192×10×18 up to 1×192×80×144. The root cause was that `prepare_conv_transpose2d_weights.cpp` computed the weight dtype but never wrote it back into `conv_config.weights_dtype`. When the DRAM slice path subsequently called `get_cb_info`, the stored config still had `weights_dtype = nullopt` and crashed. The fix wrote the computed dtype back in the missing path and added defense-in-depth guards in `TTNNOpModel.cpp` for the two affected query sites. After this fix, all four ConvTranspose2d ops compiled and ran cleanly at opt_level_1 and opt_level_2.

At opt_level_2, after the ConvTranspose2d fix, the block C inference was still failing at runtime with a circular buffer clash: `Statically allocated circular buffers clash with L1 buffers on core range [0-0 - 7-6]. L1 buffer allocated at 171520 and static circular buffer region ends at 177440`. This did not reproduce at opt_level_1 because the Conv2d ops use DRAM placement at that level. The root cause was a structural gap in the L1SpillManagement simulation called the dead zone. The simulation's virtual address floor sits at real address 173,484 (`l1_size − l1BudgetPerCore`), but circular buffers physically start at `l1_unreserved_base = 103,712`, leaving a 69,772-byte region that the simulation cannot track. One of the large Conv2d ops in the block had a CB peak usage of 73,728 bytes, meaning its CB extended 3,956 bytes into this untrackable region. When actual runtime L1 pressure exceeded the simulation budget by just 1,964 bytes (due to lazy deallocation and program cache overhead), a tensor was placed at real address 171,520 — inside the CB region ending at 177,440. Because that address was below the simulation floor, the overlap check could not see the tensor and the op remained in L1, causing the runtime crash. The fix adds a pre-check in the simulation: if an op's CB peak usage exceeds the dead zone, the op's CBs reach into territory the simulation cannot track, so it is forcibly demoted to DRAM. Live L1 inputs are evicted first to maintain homogeneous input/output memory layouts for downstream ops. With this fix all Block C tests pass at opt_level_0, opt_level_1, and opt_level_2.
