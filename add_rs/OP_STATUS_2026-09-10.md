# conv2d: the two asserts fixed, a third blocker exposed (2026-09-10, later)

## Fixes applied (4 files, all in tt-metal)

| File | Change |
|---|---|
| `.../quasar/halo/device/kernels/dataflow/halo_gather.cpp:259` | `constexpr` → `const` — it is a per-node **runtime** arg, registered in `runtime_arg_schema` at `untilize_with_halo_program_factory.cpp:499` and given a per-node value at 609. |
| `tt_metal/impl/dataflow_buffer/dataflow_buffer.hpp` | new `bool is_self_loop = false;` on `DataflowBufferConfig` |
| `tt_metal/impl/dataflow_buffer/dataflow_buffer.cpp:2032` | overlap check becomes `if (!is_intra_tensix && !config.is_self_loop)` |
| `tt_metal/impl/metal2_host_api/program_spec.cpp` | plumbs the already-computed `is_self_loop` into the config |

Why the overlap assert was wrong, not the op: `program_spec.cpp:2562` already computes
`is_self_loop`, but grants the exemption only when the self-looping kernel is *compute*
("A DM self-loop (Gen1-only) needs no tensix_scope"). `halo_gather` is a data-movement
kernel and the factory deliberately self-loops its DRAM-config scratch — its own comment
at `untilize_with_halo_program_factory.cpp:459` says so. The overlap is legal:
`ClientTypeAllocator::allocate_for_consumer` (`dataflow_buffer.cpp:1004-1017`) keeps
clientR != clientL even when both sides are the same RISC, because client type is a
credit-flow endpoint id, not a processor id. A separate flag is used rather than
`tensix_scope = INTRA` because INTRA takes the Tensix packer→unpacker remapper path
(`dataflow_buffer.cpp:2066+`), which is wrong for a DM kernel.

Both fixes build clean and conv2d no longer asserts.

## What conv2d does now: hangs later, in a pre-launch barrier

Stack at a 50-minute timeout (`logs/conv_after_both_fixes.log`, exit 124):

```
conv::run(Conv2dOp) -> quasar::conv2d -> quasar::detail::conv2d_DRAM
  -> quasar::op_slicing::run_sliced_op        <- past the halo entirely
  -> quasar::to_memory_config
  -> prim::qsr::sharded_to_interleaved        <- a LATER conv stage
  -> EnqueueMeshWorkload -> SDMeshCommandQueue::enqueue_mesh_workload
  -> SDMeshCommandQueue::wait_for_cores_idle()
  -> tt::llrt::internal_::wait_until_cores_done  -> Cluster::read_core
  -> libttsim_clock_all_devices
```

`wait_for_cores_idle` is a **pre-launch barrier for the previous workload's cores**. One
core never reports done. And per `tt_metal/llrt/llrt.cpp:380-382`:

```
// timeout_ms == 0 means infinite wait on sim; on silicon it means use configured
// operation timeout.
if (timeout_ms == 0 && !is_simulator) { timeout_ms = ...; }
```

the wait is **unbounded on the simulator by design** — so this run would never have
returned. 100% CPU for 50 minutes is the host polling while the simulator clocks.

Same class as the known FP32 tilize hang (a core finishes its work without setting
`RUN_MSG_DONE`), but reached in bf16, at conv2d's `sharded_to_interleaved` step.

**Not a hardware error.** Bug 1 was a C++ declaration mistake; bug 2 an over-broad host
assertion; this third one is an unbounded wait for a core that never reports completion.

# conv2d, 5th blocker: root cause found, and it is a DRAM-layout consequence

Identified by adding a temporary `DFBDIAG` log in `program_spec.cpp` that names every
DFB next to its entry_size. Every DFB in the run is a clean 2048 except three:

```
DFBDIAG name=cb_in     entry_size=2080 num_entries=2 self_loop=false
DFBDIAG name=cb_tilize entry_size=2080 num_entries=2 self_loop=true
DFBDIAG name=cb_out    entry_size=2080 num_entries=2 self_loop=false
```

Those are the mainline **tiled** permute factory's DFBs
(`permute_tiled_program_factory.cpp:764-787`), sized at line 758:

```cpp
uint32_t input_page_size = detail::tile_size(tensor_return_value) + misalignment;
```

and `misalignment` (line 664-666):

```cpp
uint32_t subtile_line_bytes = face_shape[1] * element_size;             // 16 * 2 = 32
uint32_t read_alignment = detail::get_buffer_alignment(input_tensor);   // DRAM -> 64
uint32_t misalignment = read_alignment > subtile_line_bytes             // 64 - 32 = 32
                            ? read_alignment - subtile_line_bytes : 0;
```

So 2048 + 32 = 2080. The 32 bytes are read-staging headroom: a DRAM read must start on a
64-byte boundary, so fetching a 32-byte subtile line overshoots by 32 and the destination
entry needs slack. A Gen1 circular buffer tolerates the resulting non-tile page; Quasar's
Tensix reaches this buffer through the tile-indexed TDMA path, which requires
`entry_size % tile_bytes == 0` (`tensix.cpp:14501`).

## The decisive detail

`get_buffer_alignment` (line 84-87) returns the **DRAM** alignment (64) only because the
permute input is in interleaved DRAM. For an **L1** input it returns 16, which is below
`subtile_line_bytes`, so `misalignment = 0`, `input_page_size = 2048`, and the constraint
is satisfied **with no code change at all**.

This blocker is therefore a consequence of running everything in interleaved DRAM at
grid `<1x1>`. It resolves itself under the L1-sharded layout Quasar is designed for --
the sharding work already identified as the remaining architectural task.

## Attempted and reverted

Rounding `input_page_size` up to a tile multiple on Quasar made conv2d **run end to end**
(no assert, no hang, a tensor came back) but the result was **all zeros**
(`pcc=nan max_rel_err=1.00000`). Cause: the kernel receives only tile/face geometry as
compile args (lines 855-873), not the page size, so it walks tiles at 2048 while the
reader uses the DFB's 4096 stride. Reverted -- a silently wrong answer is worse than a
loud error.

The remaining alternative is to relocate the staging headroom outside the tile-addressable
entry. That changes a factory/kernel contract in mainline permute shared with Wormhole and
Blackhole, and cannot be validated here without the Wormhole permute suite.

## Net

conv2d does **not** correctly run on Quasar. It gets through dispatch, kernel JIT, the
halo, op_slicing and the compute-config check, and stops at the permute DFB entry-size
constraint. Nothing found so far is a hardware limitation.

# Quasar matmul localised: compute is correct, the output writer never consumes

Instrumented the matmul compute and writer kernels with `DPRINT` (fmt-style `{}`
placeholders -- printf `%u` fails a compile-time check in this tree) and ran
`matmul_1tile` (32x32 @ 32x32, single tile) against the quasar-tip simulator.

## The compute kernel is fine

```
N0TR1 (MATH):  matmul_block                                  <- the matmul runs
N0TR2 (PACK):  pack alive -> g1 pre in0/in1 wait -> g2 inputs ready
               -> g3 last_out, pre reserve -> g4 reserved
               -> g5 pre pack_block cb=2 n=1 untilize=0
               -> g6 packed -> g7 pushed
```

So MATH computes, PACK reserves, packs one tile into cb=2 and pushes it. `untilize=0`,
so `reblock_and_untilize` is correctly not used. Nothing in the compute kernel is stuck
or skipped.

## The writer never runs its output loop

`reader_bmm_tile_layout_in1_sender_writer_padding_metal2.cpp` carries the output write
(`cb_out.wait_front` -> `noc.async_write` -> `async_write_barrier` -> `pop_front`,
lines 430-458). The watcher confirms it **is launched** (index 8 in
`generated/watcher/kernel_names.txt`), but with a fresh kernel cache and DPRINT enabled
it produces **no output at all**, not even a probe placed as the first statement of
`kernel_main`, while the compute kernel's probes in the same run all fire.

So the result is packed into cb=2 and never written to DRAM, and the output buffer is
returned as zeros. That is the whole of the `pcc=nan max_rel_err=1.0` result.

## Why this is #48552

The kernel's own comment at line 664 describes exactly this region:

```
// [#48552] Compute-side finish() REMOVED: it wedged on PACK ... and
// untilize_mode_out_cb.finish() waits on the output writer. Credit drain-on-exit is
// kept only on the DM producer/consumer kernels.
```

The compute/writer credit handshake on the output buffer is the open defect. This adds
one fact the comment does not have: the compute side completes and pushes; it is the
consuming writer that does not proceed. Fixing it means choosing the intended handshake,
which is the issue owner's call -- a guess here silently corrupts results rather than
failing, which is exactly what happened when a page-size guess was tried earlier.

Reproducer: `add_rs/probe_exec_one_op.py matmul_1tile`, ~40 s, single tile, no conv2d.

# BREAKTHROUGH: matmul works on Quasar by selecting a different program factory

The zeros were not a broken compute kernel -- they were the **wrong factory**.

`runtime/lib/ttnn/operations/matmul/matmul.cpp:89` passed `program_config = std::nullopt`,
so Quasar auto-selected the **mcast-1d** factory, whose fused in1-sender/writer
(`reader_bmm_tile_layout_in1_sender_writer_padding_metal2`) never consumes the packed
output -- the #48552 handshake. Passing `MatmulMultiCoreProgramConfig{}` explicitly picks
the simple multi-core factory, which uses a plain `writer_unary_interleaved_start_id` (the
same shape as the `Bmm` gtest that passes in the Quasar sim regression suite) *and* a
compute kernel without the `BriscThreadId` reference.

Result, same simulator, same build:

| op | before | after |
|---|---|---|
| `matmul_1tile` (32x32 @ 32x32) | `pcc=nan` (all zeros) | **PASS** `pcc=0.999902 max_rel_err=0.0084` |
| `matmul` (32x64 @ 64x32) | `pcc=nan` (all zeros) | **PASS** `pcc=0.999824 max_rel_err=0.0085` |

Both inside bf16 tolerance. **Quasar matmul now works**, which also unblocks `linear`.
This is the single highest-value op in the stack and it needed no tt-metal kernel change --
only a factory choice in our own runtime.

## conv2d is still wrong, and now for a precise reason

conv2d does **not** go through `ttnn::matmul`. `quasar::conv2d` builds its own matmul
program via `conv2d_op_sharded_program_factory` (DFBs `act`, `weights`, `act_tilized`,
`matmul_partials`, `out`), so the factory override above does not reach it, and it still
uses `bmm_large_block_zm_fused_bias_activation_metal2` with the mcast-style writer
arrangement -- the same #48552 handshake.

With fix #6 re-applied, `conv2d_1x1` now **compiles and runs** (it previously failed to
build trisc0) but returns `pcc=0.008290`.

So the remaining conv2d work is to give conv2d's own matmul the equivalent of the working
writer arrangement -- i.e. the same #48552 fix, but inside the conv2d factory rather than
selectable from our runtime.

## Note on fix #6

`get_batch_from_reader` is `0u` in every Quasar matmul factory, but the
`ckernel::ThreadId::BriscThreadId` name must still resolve because a discarded
`if constexpr` branch is fully name-checked, and the `UNPACK()/MATH()/PACK()` macros mean
it only expands on trisc0 -- exactly the "trisc0 build failed" symptom. Quasar's
`mailbox_read()` indexes a Tensix-thread-only mailbox with no DM slot, so there is no
equivalent read; the fix asserts the flag is false rather than inventing one.

# Definitive: conv2d cannot route around #48552

The `QSR_CONV_SIMPLE_MM` experiment (forcing the simple matmul factory inside conv2d) is
**invalid**, and the layout-vs-arithmetic discriminator shows why.

With the override on, conv2d_1x1 gives:

```
pcc=0.115570
SORTED-MULTISET pcc=0.978116 max_abs=1.20074 -> values genuinely differ (arithmetic)
device[0:6]=[0.0549, 0.0549, 0.0549, 0.0549, 0.0549, 0.0549]   <- constant across output channels
golden[0:6]=[1.0043, 0.8444, 0.8755, 0.8448, 0.9012, 0.6637]
```

Output constant across output channels for a fixed pixel means the weight rows are being
read as identical -- a weight *layout* misread, not bad maths. And conv2d.cpp:841 says why:

```
// For the no-spill path we need the full-inner-dim layout so it matches
// act_block_w_ntiles = full K and the ...
```

conv2d prepares its weights (`prepare_conv_weights_biases_and_move_to_device`, line 852) in
a layout **matched to the factory's block config**. Changing the factory without changing
weight preparation makes the weights unreadable. So the simple factory is not available to
conv2d the way it is to standalone matmul/linear, where operands are plain [K,N] matrices.

**Conclusion:** conv2d's activation and weight preparation are built around the mcast
factory, so conv2d cannot avoid the factory whose writer never consumes the packed output.
conv2d is blocked on #48552 itself -- the compute/writer credit handshake -- not on a
configuration choice anywhere in our stack. The override has been removed.

This is the same defect that made standalone matmul return zeros; matmul escaped it by
selecting a different factory, and conv2d cannot.

# conv2d SOLVED — the fault was never in conv2d

Written after the session that closed it. Read this section before the ones above:
several conclusions there are superseded.

## What the fault actually was

`conv2d` was numerically wrong (`conv2d_1x1_asym`: pcc `-0.057558`, sorted-multiset
`0.608719`) because of a defect in the **permute** that the Forge lowering inserts
*after* the convolution, not because of anything in the conv2d decomposition.

Every earlier attempt failed because it permuted the *weight preparation* inside
`conv2d.cpp`. Four such changes in a row produced byte-identical results, which was the
clue: the conv2d code was already right.

## How it was localised — the method that worked

Guessing at layout contracts had already produced two silently-wrong results. What
worked instead was checking an **exact invariant per op, inside the runtime**, using
`Tensor::to_vector<T>()`, which returns logical row-major elements whatever the physical
layout is:

| op | invariant |
|---|---|
| `reshape` | preserves logical order exactly → `in.to_vector() == out.to_vector()` |
| `to_layout` | same: only the physical layout changes |
| `permute` | exact CPU reference by gathering through permuted input strides |
| `conv2d` (1x1) | `out[m][n] == sum_k act[m][k] * weight[n][k]`, computed on the CPU |

One run then names the guilty op. The result on `conv2d_1x1_asym`:

```
TOLAYOUTDIAG [1,32,16,8] l0(4096) -> l1(4096)                    maxDiff=0.000000
PERMUTEDIAG  [1,32,16,8] l1 -> [1,16,8,32] l1 perm=[0,2,3,1]     maxDiff=0.000000
RESHAPEDIAG  [1,16,8,32](l1) -> [1,1,128,32](l1)                 maxDiff=0.000000
TOLAYOUTDIAG [1,1,128,32] l1(4096) -> l0(4096)                   maxDiff=0.000000
CONVDIAG     cpu-check                                           maxDiff=0.007798   (bf16 noise, maxRef=1.364)
RESHAPEDIAG  [1,1,128,64](l0) -> [1,16,8,64](l0)                 maxDiff=0.000000
PERMUTEDIAG  [1,16,8,64] l0 -> [1,64,16,8] l0 perm=[0,3,1,2]     maxDiff=1.359375   <-- the whole error
```

`1.359375` is the reported `max_abs_err` of `1.36395`. Per-swap logging then narrowed it
to one transpose:

```
SWAPDIAG (2,3) [1,16,8,64] l0 -> [1,16,64,8] l0   maxDiff=1.359375   <-- wrong (ROW_MAJOR)
SWAPDIAG (2,3) [1,16,32,8] l1 -> [1,16,8,32] l1   maxDiff=0.000000   <-- same swap in TILE, exact
SWAPDIAG (1,2) [1,16,64,8] l0 -> [1,64,16,8] l0   maxDiff=0.000000
```

## Root cause, in two parts, both in `permuteViaTransposes`

That function (`runtime/lib/ttnn/operations/data_movement/permute.cpp`) is our own
workaround: Quasar has no general `permute`, so an arbitrary permutation is realised as a
sequence of `quasar::transpose` axis swaps. Two ways it fell back into mainline
`ttnn::permute` — the op it exists to avoid:

1. **Non-adjacent swaps have no Quasar program factory.** `quasar::transpose` maps an
   axis pair to a `TransposeOpDim`, and only three of six have a factory: `WH` (2,3),
   `HC` (1,2), `CN` (0,1). `NH` (0,2), `NW` (0,3) and `CW` (1,3) delegate to mainline
   `ttnn::permute` at `quasar/transpose/transpose.cpp:128-136`. The old selection-sort
   decomposition emitted `(1,3)` = `CW` for `[0,3,1,2]`.
2. **`WH` on a ROW_MAJOR interleaved tensor also delegates.**
   `quasar/transpose/transpose.cpp:142-145`: `if (interleaved_rm) return prim_permute(a,
   {0,1,3,2})`. In TILE the same swap goes to `transpose_wh_program_factory` and is exact.

Neither delegation fails loudly on Quasar — it returns wrong data. Run on its own, the
same permute (`permute_nhwc2nchw_subtile`) **hangs** in the simulator.

## The fix

Both parts are in `permute.cpp`:

1. Insertion sort instead of selection sort, so only **adjacent** swaps are emitted.
   Adjacent transpositions generate the symmetric group, so this is always possible. For
   `[0,2,3,1]` it emits the same `(1,2),(2,3)` as before, so the already-working
   NCHW->NHWC direction is unchanged; for `[0,3,1,2]` it emits `(2,3),(1,2)` instead of
   the broken `(1,3)`.
2. If any emitted swap touches the last axis and the tensor is ROW_MAJOR, tilize for the
   duration of the swaps and restore ROW_MAJOR at the end. Sequences that never touch the
   last axis (`HC`, `CN`) are already correct in ROW_MAJOR and skip the round trip.

# 2026-09-11: driving the full ResNet-50 op set

## The actual op inventory

From the lowered graph (`ir_dumps_opt/ttnn_onnx_resnet_resnet50_opt.mlir`), 53 conv2d
grouped into five families, plus 9 other op kinds. Two lessons came out of building probes
for them:

1. **Probe the configuration ResNet actually uses.** The standing `max_pool2d` failure
   (pcc 0.318) was a 2x2 stride-2 pool with C=3. ResNet-50's pool is 3x3 stride 2 pad 1
   with C=64, and that **passes at 0.999940**. The failure was never a ResNet blocker.
2. **Avoid degenerate probe shapes -- again.** `mean_global` on `[1,64,8,8]` lowers to
   `[1,1,64,64]`, where C and H*W are both 64, so the two axes are indistinguishable; it
   selected the W reduce. ResNet lowers to `[1,1,49,2048]` reducing dim -2, the H reduce.
   Different code path entirely. Same class of mistake as the symmetric `conv2d_1x1`
   probe recorded above.

## mean: two defects, both fixed

ResNet-50's global average pool (`ttnn.mean`, dim -2 of `[1,1,49,2048]`) was refused.

**Defect 1 -- the mainline padding fill.** `quasar::reduce` clears implicit tile padding
via mainline `ttnn::fill_implicit_tile_padding`
(`quasar/reduction/generic/generic_reductions.cpp:528`), whose program factory builds a
plain `DataMovementKernel`; Quasar refuses that outright (`kernel.hpp:418`). 49 pads to
64, so the fill always fires. `quasar::pad` is not a way around it -- it reaches the same
fill through `detail::invoke_tile`.

Fix, in `runtime/lib/ttnn/operations/reduction/reduction.cpp`: the fill is guarded by
`is_tiled` at that call site, so reduce in ROW_MAJOR when either trailing dim is
unaligned, then restore the input's layout. `quasar::to_layout` is measured to preserve
logical order exactly, so this is value-neutral.

**Defect 2 -- `PoolType::MIN` does not exist on Quasar.** With the fill skipped, the
reduce compute kernel then failed to compile: `'MIN' is not a member of
'ckernel::PoolType'`. Quasar's `PoolType` is `{SUM, AVG, MAX}`
(`tt-llk/tt_llk_quasar/llk_lib/llk_defs.h:30`); Wormhole and Blackhole also have `MIN`.
The shared reduce kernel-lib names `PoolType::MIN` in four places, in branches that are
dead on Quasar (the host lowers MIN to MAX + negate), but naming a missing enumerator is
a hard error.

Fix, in tt-metal: an `is_min_pool<pool_type>()` predicate in
`ttnn/cpp/ttnn/kernel_lib/reduce_helpers_common.hpp` that is `constexpr false` under
`ARCH_QUASAR`, used at all four sites.

Result: `mean_h_axis` **PASS 0.999830**, and at ResNet's real channel count
`mean_h_axis_2048` **PASS 0.999727**.

## conv2d stride 2: Quasar's conv2d hangs, so the fast path was widened

ResNet-50 has three 1x1 stride-2 downsample convs. `quasar::conv2d` **hangs** on them --
it writes its DFB configs and then never leaves the core barrier (SIGTERM at the 1800 s
timeout, no watchdog output).

Fix, in `runtime/lib/ttnn/operations/conv/conv2d.cpp`: the 1x1 fast path no longer
requires stride 1. A 1x1 kernel with stride s is a stride-s subsample followed by the same
matmul, so the activation is unflattened to `[N, H, W, C]`, sliced with
`quasar::slice` steps `{1, sh, sw, 1}`, and reflattened. Result: `conv2d_1x1_s2`
**PASS 0.999936**, in about two minutes rather than hanging.

## conv2d: the hang is size-dependent, so conv2d is decomposed per kernel tap

The stride-1 retry above was built on a wrong premise. Measured:

| probe | shape | result |
|---|---|---|
| `conv2d_32` | 3x3 s1 p1, 32x32 | passes through `quasar::conv2d` |
| `conv2d_3x3_s1_16` | 3x3 **s1** p1, 16x16 | **hangs** -- same `pending_tensix=24` heartbeat |

So `quasar::conv2d` hangs on problem *size*, not stride, and 16x16 is in the hanging
range. ResNet-50 runs its 3x3 convolutions at 56, 28, 14 and 7 spatial, so most of them
are. Running strided convolutions at stride 1 only converts a hanging stride-2 convolution
into a hanging stride-1 one.

**Fix: decompose any convolution into one matmul per kernel tap.**

    out[n][oh][ow][co] = sum_{i,j} sum_ci pad_in[n][oh*sh+i][ow*sw+j][ci] * w[co][ci][i][j]

Each (i, j) term is a strided slice of the zero-padded activation times a [C_in, C_out]
matrix -- the 1x1 path, which is verified. `quasar::conv2d` is no longer used at all.
Three things were needed to make it correct:

1. **Pad in ROW_MAJOR.** `quasar::pad` routes a tiled tensor through
   `detail::invoke_tile`, which calls the same mainline `fill_implicit_tile_padding`
   that Quasar refuses. `invoke_rm` does not.
2. **Slice in ROW_MAJOR.** A strided slice of a TILE tensor is wrong once the
   second-last dim crosses a tile boundary: the decomposition scored 0.999843 at 16x16
   (padded extent 18, inside one 32-row tile) but 0.918844 at 32x32 (padded extent 34,
   spanning two). Slicing before tilizing fixed it (0.999730).
3. **Sum the taps pairwise, not left to right.** Each add rounds in bf16 and a left fold
   of n terms accumulates error like sqrt(n) * eps. For the 7x7 stem that is
   sqrt(49) * 0.0039 ~= 0.027, and the measurement was 0.02803 -- pcc 0.999503 but over
   the 0.02 relative-error gate. Pairwise summation gives depth log2(n): 0.01231.

Also fixed: **return the layout the graph declares for the output**, via
`inferLayoutFromTileShape(op->out())`, not the input's. Returning ROW_MAJOR where the
graph says TILE makes downstream ops select their ROW_MAJOR program factories, several of
which are unported and refuse. Every single-op conv probe still passed with the wrong
layout; it only showed up as a refused residual add in a full block.

One tt-metal kernel fix was needed for the ROW_MAJOR pad:
`reader_pad_dims_rm_interleaved_v2.cpp` cast a uint32_t L1 address straight to a pointer,
which is `-Werror=int-to-pointer-cast` on Quasar's RV64 data-movement cores. Cast through
`uintptr_t`.

`resnet_block` -- a real bottleneck: 1x1 -> relu -> 3x3 pad 1 -> relu -> 1x1, a 1x1
projection on the skip, then add -> relu -- **PASS pcc=0.999934**. This is the probe that
caught the output-layout defect, which no single-op probe could.

# Full ResNet-50 on Quasar: compiles and executes, one op short of correct

Run with `add_rs/run_resnet50_quasar.py <input_size>`; `PROBE_OPT=1` selects the
optimised pipeline. A reduced input resolution is used deliberately -- the op inventory
is identical at any resolution, and 224x224 is not affordable in the simulator.

## What happens

**Default pipeline, 64x64 input** -- op inventory identical to the real 224x224 graph
(`add=16, conv2d=53, linear=1, max_pool2d=1, mean=1, permute=2, relu=16, reshape=4,
to_layout=50`):

- **compiles** clean
- **refuses at the global average pool**: `mean(dim_arg=[3])` on `[1,1,2048,4]` -- the
  unported W reduce factory, the one gap documented above. Single blocker.

**Default pipeline, 32x32 input** -- final feature map is 1x1, so the average pool folds
away and there is no `ttnn.mean` (the inventory also gains `typecast=5, from_device=3,
to_device=1`, so this graph is not faithful):

- **runs end to end**: 53 convolutions, 10440 program launches, no refusal and no hang
- **numerically wrong**: pcc 0.071259, max abs err 2656

So execution of the whole model is no longer the obstacle. Two things are:

1. **The W reduce** (`reduce_op_multi_core_w_program_factory.cpp`), for the average pool.
2. **A correctness bug that only appears at full-model scale.** A single bottleneck block
   measures 0.999934 and every op passes in isolation, yet 53 convolutions chained give
   pcc 0.071. Not bf16 drift -- the error is far too large. Unverified ops in that graph
   are the place to start: `from_device`, `to_device`, `typecast`, and the very small
   spatial sizes (4x4, 2x2, 1x1) the later stages reach at reduced resolution.

**Optimised pipeline: blocked at compile time, twice.**

- `set_enable_remove_dead_values(True)` crashes the compiler -- upstream MLIR assertion at
  `RemoveDeadValues.cpp:318` in `processFuncOp`. A compiler bug, not a Quasar one.
- With that off, the pipeline fails in `OperationValidationAndFallback`: the optimiser
  asks tt-metal whether each op is legal by *constructing it on the device*, and that
  query hits `DataMovementKernel is not supported on Quasar` for `ttnn.conv2d`. The pass
  is gated on `optimizerPassEnabled` (`TTNNPipelines.cpp:110`), so it cannot be separated
  from the optimiser. This happens in the compiler, before the runtime sees the op, so the
  runtime conv decomposition cannot help. It also means the optimised pipeline -- the only
  one that lowers the average pool to the working `mean(dim=[-2])` -- is unavailable until
  the constraint query works on Quasar.

# Debugging the full-model pcc drop

## It is not bf16

First check, CPU only, no device: the same torchvision ResNet-50 run entirely in
bfloat16 against its own fp32 output scores **pcc 0.999959**, the reference has
|max| 4.41 and mean |x| 1.08, and activations stay bounded through the stages
(layer1 1.2, layer2 4.2, layer3 9.9, layer4 10.1). So a device output with max abs
error 2656 against a reference of 4.41 is garbage, not rounding. Worth the 10 seconds
before instrumenting anything.

## Bisect by depth

`add_rs/run_resnet50_prefix.py <prefix>` runs a real prefix of the model --
`stem`, `l1b0`, `l1b1`, `layer1` .. `layer4` -- so the first failing prefix names the
stage. The **stem alone failed** (pcc 0.954), which is one 7x7 convolution plus a max
pool, both of which pass individually at exactly those shapes (0.999906, 0.999940).

## Cause: conv2d carries a FUSED ACTIVATION and both Quasar paths dropped it

`Conv2dConfig::activation` is read from the flatbuffer at
`runtime/lib/ttnn/operations/utils/utils.cpp:353`. The 1x1 fast path and the tap
decomposition both reimplement the convolution and neither looked at it.

The frontend fuses every relu that directly follows a convolution into it. That is why
the stem's graph has `conv2d=1` and **no `ttnn.relu` at all**, and why layer1 has
`conv2d=11` but only `relu=3` -- the three post-residual relus, the six intra-block ones
having been fused away. Dropping the activation leaves positives correct and negatives
unclamped, which is exactly the signature seen: magnitudes unchanged
(got |max| 0.5352 vs ref 0.5359) and pcc degrading with depth.

Every single-op probe missed it because a hand-written ONNX `Conv` node has nothing to
fuse, and `resnet_block` missed it because its relus are separate `Relu` nodes.

Fix: apply the activation to the finished result in both paths, via
`quasar::binary::add(x, 0.0f, lhs_activations={act})` -- the idiom the runtime's own relu
already uses on Quasar. `UnaryWithParam` converts to `EltwiseUnaryWithParam` through its
converting constructor, so parameterised activations carry over too, not just relu.

| prefix | before | after |
|---|---|---|
| `stem` | pcc 0.954417 | **pcc 0.999973**, max abs err 0.00497 on a 0.536 reference |
| `layer1` | pcc 0.339245 | pcc 0.886885 -- better, still wrong |
| full model (32x32) | pcc 0.071259 | to be re-measured |

## A harness bug found on the way

The pass gate used per-element relative error with a 1e-3 floor. After a relu most of a
tensor is exactly 0, so any tiny absolute error divides by the floor and looks enormous:
the corrected stem reports max_rel_err 0.865 while being accurate to 0.005 out of 0.536.
Replaced with error normalised by the tensor's own scale (`max_abs / ref.abs().max()`).

## Still open

`layer1` is 0.886885 -- a real error, not precision. Bisecting inside it (`l1b0`,
`l1b1`). Note that with `weights=None` the folded BatchNorm contributes bias exactly 0
and scale 1, so conv **bias is untested by this model** even though the tap path adds it.

## Second cause: the output readback untilize corrupts padded tensors over 64 tiles

With the fused activation applied, `stem` passed (0.999973) but `layer1` was still wrong
(0.886885). Bisecting again, this time by shape rather than by depth:

| probe | shape | tiles | trailing dims | result |
|---|---|---|---|---|
| `relu_nchw_64` | `[1,64,8,8]` | 64 | sub-tile | **PASS** 0.999998 |
| `relu_nchw_96` | `[1,96,8,8]` | 96 | sub-tile | FAIL 0.750191 |
| `relu_nchw_128` | `[1,128,8,8]` | 128 | sub-tile | FAIL 0.740757 |

| `relu_tiles_128` | `[1,1,512,256]` | 128 | **aligned** | **PASS** 0.999997 |
| `permute_256_inv` | out `[1,256,8,8]` | 256 | sub-tile | FAIL 0.872699 |
| `permute_256_inv_reshaped` | same permute, out reshaped to `[1,1,256,64]` | | aligned | **PASS** 0.999999 |

So the trigger is implicit tile padding plus more than 64 tiles, and it is independent of

Instrumenting confirmed it exactly. For `relu_nchw_96`: the input tilize is exact, relu's

readback untilize returns **maxDiff 0.500000** -- full scale, on data in [-0.5, 0.5). The

The culprit is `runtime/lib/ttnn/runtime.cpp:201`, `toHostSingleTensor` -- a **separate
output-readback call site** that does an on-device `quasar::to_layout(.., ROW_MAJOR)`. No
graph-level diagnostic covered it, which is why every op probe passed while whole-model
results were wrong: this is the path every model output takes, and ResNet-50's tensors are
`[1, C, H, W]` with C >= 128 throughout.

Fix: when the trailing dims are not tile-aligned on Quasar, clear `untilizeOnDevice` and
take the host untilize path that already exists a few lines below. Aligned tensors keep the
device path at any size.

All six previously-failing probes now pass (0.999992 - 1.000000), and `relu_nchw_64` is
unchanged.

## Probe-design flaw worth remembering

Every probe in `probe_exec_one_op.py` used `rand()*0.1` weights with `rand()` inputs --
**all strictly positive**, so every convolution output is positive and relu is an identity.
That is why `resnet_block` scored 0.999934 while the runtime was dropping 2 of its 3
fused relus entirely. Real ResNet-50 uses Kaiming init, so about half of every output is
negative. The fused-relu probes now use `randn` weights and `rand() - 0.5` inputs. Same
family of mistake as the degenerate shapes recorded above: a probe that cannot distinguish
right from wrong reports PASS.

## Where the pcc drop stands

| stage | dropped activation | + activation fix | + readback fix |
|---|---|---|---|
| `stem` | 0.954417 | 0.999973 | **0.999973 PASS** |
| `layer1` | 0.339245 | 0.886885 | 0.967274 |
| full model, 32x32 | 0.071259 | -- | **0.825961** |

Two root causes found and fixed; both were invisible to single-op probes. What remains is
smaller and looks like accumulation rather than a single broken op: a single convolution
through the tap decomposition measures err/scale ~0.010 (`conv2d_32`, 0.999826), and ~1%
per convolution compounding over 53 of them is consistent with 0.826.

The reason the tap decomposition is about an order of magnitude less accurate than the
values themselves deserve: it sums kh*kw separate matmul results with bf16 tensor adds,
and each add rounds at the magnitude of the running total, whereas a real convolution
accumulates all kh*kw*C_in products inside one fp32 destination accumulator.

- **fp32 accumulation: tried, refused.** Asking the tap matmuls for a `FLOAT32` output
  makes both `conv2d_32` and `conv2d_stem` come back `QUASAR_REFUSED` (the f32 path goes
  through the SFPU). Reverted; the finding is recorded in a comment at the call site.
- **The real fix is im2col**: one matmul with `K = kh*kw*C_in`, so the sum happens inside
  the matmul's accumulator instead of across bf16 adds. It needs the tap slices
  concatenated along the channel axis, and Quasar has no `concat` -- `slice_write` into a
  preallocated buffer is the available route. Not attempted.

## Also found, not fixed: from_device hangs on a tiled sub-tile tensor

The readback fix routes unaligned trailing dims to the host untilize path, and for one
prefix (`l1b0`, stem + one bottleneck) that path then **hangs in
`ttnn::from_device`** on a TILE `[1,256,8,8]` tensor -- markers show the add and relu
complete, the readback enters the host path, and `from_device` never returns. So for that
shape class the device untilize corrupts and the host transfer hangs.

It is not systemic: the same code path completes for `relu_nchw_256` and for the whole
32x32 model. Reproduce with `run_resnet50_prefix.py l1b0`.

## Third cause: the device ROW_MAJOR -> TILE conversion corrupts some shapes

`layer1` was still 0.967274 with the first two fixes, against a **measured ceiling** of
0.999949 -- torch bf16 vs fp32 on the same prefix (see below), so this was a real defect,
not precision.

Bisecting by structure rather than by depth found it. A bottleneck block with a
**projection** skip passes (0.999990), but ResNet's blocks 2 and 3 of every stage use an
**identity** skip, and `run_resnet50_prefix.py idblock` -- torchvision's own `layer1[1]`
alone -- failed at **0.811022**. Instrumenting each op in it:

| op | result |
|---|---|
| conv1 1x1 256->64 (relu fused) | correct, maxDiff 0.031 of maxRef 6.13 |
| conv2 3x3 64->64 (relu fused) | correct, maxDiff 0.051 of 6.36 |
| **conv3 1x1 64->256** | **wrong: maxDiff 3.771 of 4.55, 7694/16384 elements** |
| add (verified against its own operands) | exact, 0.0156 |

The bad elements covered all 256 output channels but only spatial positions 0..31 of 64 --
exactly the first of two tile-rows. Splitting operand prep from the matmul showed
`actDiff=5.65625`: the *activation* handed to the matmul did not hold its input's values.
Narrowing to the single call:

```
GTOLAYOUT  [64,64] l1 -> l0  diff=0.000000    the graph's untilize is exact
TILIZEDIAG [64,64] via=tilize diff=5.656250   tilizing it back is wrong
TILIZEDIAG [64,256] via=tilize diff=0.000000  same graph, same run, exact
```

So **Quasar's device ROW_MAJOR -> TILE conversion corrupts a 64x64 bf16 DRAM tensor**,
confined to the first tile-row, while 64x256 is exact. Ruled out along the way:
`quasar::tilize` and `quasar::to_layout` give **byte-identical** wrong results (they share
the device op), a `distributed::Synchronize` barrier makes no difference, and the memory
configs, sharding, padded shapes and layouts of the good and bad cases are identical.

Fix: tilize the activation through `Tensor::from_vector` -- host tilize then copy down,
the route the weight already used. `idblock` goes from 0.811022 to **0.999975**, with
conv3's maxDiff 3.771 -> 0.019 and 0 bad elements. It costs a host round trip per
convolution, which is slow but correct; the device path can return once tt-metal's
conversion is fixed.

## Emulator resource discipline (learned the hard way)

- A killed run **orphans** the aether/zrun job on `soc-l-04`, which keeps holding its ZeBu

  `Waiting for ack msg from remote...`. It happened here and cost ~25 minutes.
- **`bjobs` does not show it.** That is LSF; the Quasar job runs under Altair VOV. `bjobs`

# 2026-09-13: the permute rotation route was wrong, and how a stale compiler hid it

## What happened

After removing the fitted `>=8` bound from the tilize host route, a craq-sim re-run
showed **every** conv probe and `max_pool2d_resnet` failing -- ops that had passed
minutes earlier. `max_pool2d_resnet` does not go near `conv2d.cpp`, so the blast
radius alone ruled out that day's edits.

The bisect, in order, and each step's cost:

1. **Simple ops still passed** (`relu` 1.000000, `matmul` 0.999824, `reshape`,
   `transpose_2d`). So the environment was intact and the regression was selective.
2. **Reverting the op trace changed nothing** -- byte-identical pcc (0.269536).
3. **Disabling the tilize host route changed nothing** for maxpool -- again
   byte-identical 0.269536. On craq-sim the device tilize is correct, so the host
   route and the device route agree there; the route is numerically a no-op on the
   simulator and can never explain a simulator-only difference. That should have
   been obvious a step earlier.
4. **A full log diff** of the passing 00:56 run against the failing one showed the
   two runs identical line for line -- same kernels, same DFB writes, same dispatch
   -- differing only in timestamps and the final numbers. Same program, different
   data.
5. **Narrowing by op** found the boundary: `permute_generic` (tile-aligned) passed,
   the two **sub-tile** 4-D permutes failed at 0.54 / 0.48, having passed at
   0.999996. Every failing op's graph contains a sub-tile permute.
6. **Disabling the rotation route restored them both to 0.999996.**

## The actual defect

The rotation route rewrites a single-axis rotation as one WH transpose between two
reshapes. It was gated on the **merged** extents being at least a tile:

    m[m.size() - 1] >= TILE_WIDTH && m[m.size() - 2] >= TILE_HEIGHT

That is the wrong invariant. `permute_nchw2nhwc_subtile` is `[1, 32, 16, 8]` with
perm `(0, 2, 3, 1)`; the merge is `[32, 128]`, which clears the gate -- and the
route is still wrong, because the gate says nothing about the tensor being
reshaped. A TILE tensor whose logical trailing dims are 16 and 8 carries implicit
tile padding to 32x32, so a reshape to `[32, 128]` is not a physical no-op: it has
to repack. The condition that matters is that the **input's own trailing dims** are
tile-aligned, so the reshape moves no data.

This also explains the earlier 2x2 / 4x4 convolution regression that the merged-extent
gate was fitted to. Those merges produce a trailing extent of 4, so the gate excluded
them and the symptom went away -- but the cause was never the merged extent, it was
the unaligned input. One fitted bound, two symptoms, wrong invariant both times.

## Why it looked like a new regression

`cmake --build build --target install` relinked `libTTMLIRCompiler.so` (648 ninja
steps, TableGen included). The previously installed compiler was stale relative to
the source tree, so the graphs fed to the runtime changed under a fixed source. The
sub-tile permutes had been passing against the older graphs.

**The lesson is not about the rotation route.** It is that `deploy_only.sh` rebuilds
only `TTMLIRRuntime`, so the installed compiler drifts from the source tree for as
long as nobody runs a full install -- and every measurement in between is taken
against a compiler nobody can name the version of. A full `--target install` before
a measurement campaign, not in the middle of one.

## Diagnostic rules this run confirmed

- **Byte-identical results mean the edited code is not in the causal path.** Used
  three times here, correct three times.
- **A workaround that cannot change behaviour on a target cannot explain a failure
  on that target.** The host tilize route is a no-op on craq-sim by construction.
- **Diff the whole log, not the result line.** Two identical execution traces with
  different numbers pointed straight at data, not dispatch.

## The second defect: a tiled reshape that only relabels

With the rotation route disabled the permutes were right, but every convolution
with sub-tile spatial dims was still wrong, and `conv2d_32` (32x32 spatial) was
fine. Instrumenting the 1x1 path settled where it was *not*:

    [convcheck] act_vs_input n_in=1024 n_act=1024 max_abs=0.000000 first_bad=-1
    [convcheck] M=4 K=256 N=1024 matmul_pcc=0.999998 max_abs=0.003888
    [convcheck] out spec MATCH: got padded=[1,1,32,1024] ; want padded=[1,1,32,1024]

The activation reaching matmul is the input exactly, the matmul is right against
a host reference, and the tensor handed back carries the declared spec. Note the
first check exists because the second cannot stand alone: a matmul checked
against a reference computed *from* `act` agrees with itself when `act` is
corrupt.

The error map named the axis:

    ERRMAP bad=1768/4096 shape=(1, 1024, 2, 2)
    ERRMAP h=0 bad_per_w=[0, 0]
    ERRMAP h=1 bad_per_w=[871, 897]

The first spatial row is perfect and the second is entirely wrong. Checking the
reshape op's own invariant -- a reshape is a relabelling, so `to_vector` must
return the identical sequence -- found it on the **input** side:

    [reshapecheck] n_in=1024 n_out=1024 in_layout=TILE max_abs=0.978516 first_bad=512

`[1,2,2,256] -> [1,1,4,256]`, and everything from element 512 (row 2 of 4) on is
someone else's data.

**Why.** A TILE tensor stores a row at `prod(leading) * roundup(H, 32) + h`, so
the implicit padding after a sub-tile H is part of the address. `[1,2,2,256]`
occupies two tile rows with two valid rows each (physical rows 0,1 and 32,33);
`[1,1,4,256]` wants four consecutive rows in one. Quasar's reshape only
relabels, so rows 2 and 3 read padding. This is the input reshape of **every**
NCHW convolution graph with sub-tile spatial dims, and the error flows through
the convolution to the second spatial row of its output.

The fix in `reshape.cpp` keeps the device path for the cases that are genuinely
free -- the last dim unchanged, and either H unchanged (only leading dims
regroup, which moves no row) or H tile-aligned on both sides -- and rebuilds
through host logical data otherwise.

This one defect explains all of: the sub-tile convolutions, `max_pool2d_resnet`,
and `permute_via_reshape_wh` (0.556086 -> 0.999999), which is the rotation
identity written out in ONNX.

## The rotation route is gone

With the reshape fixed, the rotation route *still* failed the sub-tile permutes
(0.542870 / 0.481315) -- it calls `quasar::reshape` directly from `permute.cpp`
and so never sees the op-level fix. It was added to avoid HC transposes on the
theory that HC was the emulator blocker; that theory was disproved (the cause
was the graph's `to_layout`), and the route has since been the direct cause of
two regressions. Removed, along with `rotationMergedShape`. The generic
adjacent-swap path handles every case measured.

`conv2d_3x3_sp4` first came back as nan/inf, but that was the **batch session**,
not the op: it had run second, after the nine-tap pool decomposition, in the same
device session. Run on its own it gives 0.999991, matching craq-sim exactly, and
the instrumentation is clean throughout:

    [nonfinite] after_pad   n=4608  bad=0
    [nonfinite] tap00_act   n=2048  bad=0
    [nonfinite] tap00_wt    n=16384 bad=0
    [nonfinite] tap00_term  n=2048  bad=0

The same pair in one session passes on craq-sim, so this is specific to the
emulator: a heavy decomposition leaves the next model in the session reading
memory nobody wrote, and ZeBu DRAM is not zero-initialised the way a simulator's
is, so that reads as inf rather than as zero.

**Batching ops into one device session saves a ZeBu reservation but is not free.**
Put the heavy decompositions last, or give them their own session, and treat an
inf from a later op in a batch as suspect until it is reproduced alone.

dominated by rows-per-core rather than by op count.

fallback and describes the full part; when a device is attached -- simulator or
emulator -- the compiler uses the live builder, which reports the truth for that
target. The emulator's reduced topology never reaches the mock.

# 2026-09-13: the untilize, and why ResNet-50 sat at 0.88

## The chase

`layer3` was the first stage to break (0.999903 at `layer2` -> 0.837762). Inside it,
block 0 was fine (0.999888) and block 1 was not (0.951957). One identity block on
its own reproduced it (0.890992), and `l3chain1` -- a **single 1x1 convolution**,
1024->256 at 2x2 spatial with bias -- reproduced it at 0.822046.

Then every single thing checked out:

    [convcheck]  weight K=1024 N=256 bad=0 max_abs=0.000000
    [convcheck]  act_vs_input n=4096 max_abs=0.000000
    [convcheck]  M=4 K=1024 N=256 matmul_pcc=0.999997
    [convcheck]  tail flat->out max_abs=0.000000
    [convcheck]  out spec MATCH
    [reshapecheck]  both reshapes max_abs=0.000000
    [permutecheck]  both permutes bad=0

Precision was ruled out with numbers rather than argument: a **bf16 running
accumulator** -- rounding after every one of 1024 additions, the worst realistic
case -- gives pcc 0.999680 on this convolution. The device gave 0.944937, 4.6x
worse. Not bf16.

Both simulator builds gave byte-identical 0.944937, so not a simulator artifact.

## The defect

The one op type never checked was the layout conversion itself. Adding the same
logical-identity invariant (`TTMLIR_LAYOUT_CHECK=1`) found it immediately:

    [layoutcheck] 4x1024 TILE -> ROW_MAJOR  n=4096 bad=1024 max_abs=0.500000 first_bad=512
    [layoutcheck] 4x256  TILE -> ROW_MAJOR  n=1024 bad=0

**Quasar's device untilize corrupts a sub-tile-height tensor from tile column 16
onward.** `[1,1,4,1024]` is 32 tile columns wide and loses a quarter of itself
starting at element 512; `[1,1,4,256]` is 8 wide and is exact.

That untilize sits immediately before `ttnn.conv2d` in **every** NCHW convolution
graph. Any convolution with a wide enough activation was handed a quarter-wrong
input -- and then computed the wrong answer faithfully, which is why every check
inside the convolution agreed with itself.

The host route in `quasarTilizeNeedsHostRoute` had only ever guarded
ROW_MAJOR -> TILE. Extended to both directions.

## Cascade

| | before | after |
|---|---|---|
| `conv1x1_down` | 0.944937 | **0.999995** |
| `l3idblock` | 0.890992 | **0.999971** |

were never exercised. Probe shapes have to span the model's real channel counts,
not just its real operators.

## Golden and CPU agree; the device was the outlier

`add_rs/cpu_bf16_reference.py` runs the same model on CPU in the device's precision
(bf16) against the fp32 golden. That is the floor: it is what bf16 costs, with no

| prefix | bf16 on CPU | device (before) | device (after untilize fix) | after fused conv |
|---|---|---|---|---|
| `stem` | 0.37% | 0.93% | 0.93% | **0.52%** |
| `layer1` | 0.76% | -- | 2.22% | 2.22% |
| `layer2` | 0.70% | -- | 3.68% | 4.26% |
| `layer3` | 1.04% | 45.0% | 6.07% | 6.07% |
| `layer4` | 0.86% | 54.6% | 7.11% | 7.11% |

(err/scale. pcc for the full model: **0.881799 -> 0.999901 -> 0.999918**.)

bf16 on CPU costs ~1% and **stays flat with depth**. The device's error grows. So
golden and CPU match, and the device did not -- which is what the untilize fix
addressed, and what remains is characterised below.

## The tap sum, quantified then fixed

Predicted on CPU for a 3x3 256->256 convolution at 2x2 spatial: bf16 floor
err/scale 0.00256, bf16 pairwise tap sum 0.00560. The device measured **0.00557** --
a match to three digits, so the tap summation was the whole of that convolution's
excess.

`conv2d.cpp` now builds the im2col matrix on the host and issues **one** matmul with
K = kh*kw*C_in, so the summation happens inside the matmul's fp32 accumulator
instead of across bf16 tensor adds. Quasar has no concat, and slice_write per tap
would have kept the per-tap launches this removes.

Two wins: the 7x7 stem's error halved (0.93% -> 0.52%), and craq-sim program
launches fell from **10623 to 3621** -- a 2.9x cut that matters most on the
emulator, where each launch is ~20 s.

## The residual is a systematic gain error, and it is NOT truncation

Fitting `got = a*ref + b` shows the device output is systematically **scaled down**:

| | slope |
|---|---|
| `relu` (no arithmetic) | 0.999988 |
| `conv2d_32` | 0.999599 |
| `conv2d_1x1_sp2` | 0.997076 |
| `conv2d_3x3_sp2` | 0.997194 |
| `multiply` | 0.997534 |
| `matmul` | 0.993453 |
| `layer2` (composed) | 0.965849 |
| `layer4` (composed) | 0.940172 |

Round-to-nearest is unbiased and cannot do this, and the slope matches the
top-half-values ratio to four digits, so it is uniform attenuation rather than a
few outliers. relu, which does no arithmetic, is neutral -- so it enters through
the math pipeline.

**Truncation toward zero was the obvious explanation and it is wrong.** Simulated
on CPU for the `matmul` probe: round-to-nearest gives slope 0.998296, truncation
gives 0.936806, and the device gives **0.993453** -- far closer to round-to-nearest.
So the packer is rounding, not truncating, and the residual ~0.2-0.65% per op comes
from somewhere else in the math path.

That is below the runtime: it lives in the Quasar LLK/pack path, not in op dispatch.
It is the remaining gap between the device and the bf16 floor, and it is what keeps
the full model at pcc 0.99992 rather than the ~0.99998 CPU bf16 achieves.

any timeout.

## Root cause, and it was mine

Op 14 and op 16 of the graph:

```mlir
%4 = "ttnn.to_layout"(%3) : (tensor<1x1x1x1024xbf16, #ttnn_layout21>)
                         -> tensor<1x1x1x1024xbf16, #ttnn_layout25>
%5 = "ttnn.to_device"(%4, %0)
```

and the declared output layout:

```mlir
#ttnn_layout25 = ... memref<1x32x!ttcore.tile<32x32, bf16>, #system_memory>
```

**`#system_memory`** — the compiler declares that `to_layout`'s result is a *host*
tensor, and follows it with an explicit `ttnn.to_device`. That tensor is
`[1,1,1,1024]`: second-last extent 1, never tile-aligned, so the Quasar tilize host
route fires. And the host route did this unconditionally:

```cpp
out = ::ttnn::Tensor::from_vector(std::move(hostData), spec, inputTensor.device());
```

It always passed a device pointer, so it always produced a **device** tensor —
ignoring the declared memory space. Op 16 was then asked to `to_device` a tensor
already resident on the device, and blocked forever.

Other ops in the runtime guard on `inSystemMemory(op->out())` (`conv2d.cpp:128`,
`transpose.cpp:23`, …). The host route did not. Fixed:

```cpp
::ttnn::MeshDevice *const target =
    ::tt::runtime::ttnn::utils::inSystemMemory(op->out()) ? nullptr
                                                          : inputTensor.device();
out = ::ttnn::Tensor::from_vector(std::move(hostData), spec, target);
```

Why it only ever showed up in the full model: single-op probe graphs keep every
intermediate on the device, so no `to_layout` in them declares a system-memory
output. It takes a graph with const-eval'd, host-resident weights to produce one —
which is exactly what ResNet-50 does and no probe did.

## So: why can't the full model run on the emulator?

Ordered by what actually stops you:

1. **A `to_device` deadlock at op 16** — the host route handed a device tensor where
   the graph declared a host one. Root cause found, fix written, verification blocked.
   *This, not time, is what stopped all three runs.*
2. **One worker core.** `grid = 1x1` measured from the emulator's own descriptor.
   All 53 convolutions serialise onto a single Tensix.
3. **A 1.4 h remote cap** by default (`EMULATOR_TIMEOUT=5000`), raisable — 25200 was
   used here.
4. **Weight volume is input-size independent.** 25.6M parameters = 51.1 MB in bf16
   plus const-eval programs. Shrinking 224 → 8 does nothing about it. This is why a
   pretrained run spent 65 minutes without leaving the prologue.

Items 2–4 are real constraints and were correctly identified. But item 1 is the one
that was actually firing, and it was a bug rather than a limit — which is only
visible once the op trace names the stalling op instead of the rate being
extrapolated.
